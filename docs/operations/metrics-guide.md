# Per-Client Pipeline Metrics Guide

## Overview of Pipeline Metrics

These metrics are generated by the per-client pipeline architecture in the STT Vosk Service. Each client gets an individual pipeline with dedicated resources, providing complete isolation and easier monitoring.

## Architecture Overview

```
PipelineManager
├── Client Pipeline 1 (client_id: "user_123")
│   ├── Individual Vosk Recognizer
│   ├── Dedicated Audio Queue
│   ├── Async Processing Task
│   └── Circuit Breaker Protection
├── Client Pipeline 2 (client_id: "user_456")
│   └── ...
└── Automatic Resource Cleanup
```

## Key Metrics Explained

### **Pipeline States**
- **`active`**: 🟢 Pipeline actively processing audio
- **`idle`**: 🟡 Pipeline created but no recent activity (will be cleaned up)
- **`initializing`**: ⚡ Pipeline starting up
- **`shutting_down`**: 🔄 Pipeline being cleaned up
- **`terminated`**: ❌ Pipeline terminated

### **Performance Metrics**
- **`chunks_processed`**: Total audio chunks processed by this client
- **`final_results`**: Number of final transcription results
- **`partial_results`**: Number of partial/interim results
- **`avg_processing_time_ms`**: Average processing time per chunk
- **`queue_size`**: Current audio queue size for this client

### **System Metrics**
- **`total_pipelines`**: Total number of client pipelines
- **`active_pipelines`**: Pipelines currently processing audio
- **`utilization_percent`**: (total_pipelines / max_clients) * 100
- **`max_clients`**: Maximum concurrent clients allowed

## Architecture Benefits

### **🎯 Complete Client Isolation**
- Each client has dedicated Vosk recognizer
- Individual audio buffer prevents interference
- Independent processing tasks
- No shared resource contention

### **🔧 Easier Debugging**
- Client-specific metrics and logs
- Isolated error handling
- Clear resource ownership
- Simplified troubleshooting

### **📈 Better Resource Management**
- Automatic cleanup of idle pipelines
- Configurable client limits
- Resource allocation transparency
- Memory leak prevention

### **⚡ Improved Performance**
- No worker load balancing issues
- Predictable resource allocation
- No client interference
- Optimal resource utilization

## Troubleshooting Guide

### **High Memory Usage**
```bash
# Check for too many idle pipelines
curl http://localhost:8000/ws/pipeline-distribution

# Look for high queue_size values
# Check utilization_percent
```

### **Client Connection Issues**
```bash
# Check if max_clients limit reached
curl http://localhost:8000/ws/pipeline-health

# Monitor pipeline creation/cleanup
docker-compose logs -f server | grep "Pipeline"
```

### **Performance Issues**
```bash
# Check avg_processing_time_ms for individual clients
curl http://localhost:8000/ws/pipeline-distribution

# Monitor circuit breaker status
curl http://localhost:8000/ws/stats
```

## Configuration Tuning

### **Environment Variables**
```bash
# Maximum concurrent clients
MAX_CONCURRENT_CLIENTS=50

# Audio queue size per client
AUDIO_QUEUE_MAXSIZE=100

# Pipeline idle timeout
PIPELINE_IDLE_TIMEOUT=300

# Model path
VOSK_MODEL_PATH=model/Transcription/en-model
```

### **Performance Tuning**
- **High load**: Increase `MAX_CONCURRENT_CLIENTS`
- **Memory constraints**: Decrease `MAX_CONCURRENT_CLIENTS` or `AUDIO_QUEUE_MAXSIZE`
- **Frequent disconnects**: Adjust `PIPELINE_IDLE_TIMEOUT`
- **Processing latency**: Monitor `avg_processing_time_ms` per client

The per-client pipeline architecture provides superior monitoring, debugging, and resource management compared to shared worker pools!
